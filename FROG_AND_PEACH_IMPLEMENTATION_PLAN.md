## Global Rules For Every Phase

- Prioritise phases in order. Finish security and test-safety work before refactors.
- Keep each PR or commit scoped to one phase, or to one extraction inside Phase 6.
- Do not replace Cloudflare Pages, D1, React/Vite, or the single-package structure.
- Do not introduce Express, Next.js API routes, a separate Node backend, or SaaS auth.
- Do not run E2E against production. Use an explicit local or staging `E2E_BASE_URL`.
- Do not apply D1 migrations automatically. New SQL files in `migrations/` are applied manually.
- Do not edit `public/themes/` or `public/custom-pages/` by hand. They are generated by prebuild sync scripts.
- Prefer `npm test` plus direct `tsc`/`vite build` checks during focused changes. Use `npm run build` when you intentionally want the prebuild sync hooks to run.
- If a command rewrites tracked generated files unexpectedly, stop and inspect `git status` before continuing.
- Security review anchors: origin/CSRF checks are in `src/api/router.ts`; sessions/admin unlock are in `src/api/auth.ts`; protected static paths are in `functions/_middleware.ts`; destructive module deletion is in `deleteModuleData()` in `src/api/data.ts`.

## Sub-Agent Guidance

Use sub-agents when a phase has independent work that can run in parallel without touching the same files. Keep write scopes disjoint and tell workers not to revert or overwrite other edits.

Good uses:

- Auth/origin/session audit: read-only explorer over `src/api/auth.ts`, `src/api/router.ts`, and `functions/_middleware.ts`.
- D1/destructive data audit: read-only explorer over `migrations/`, `src/api/data.ts`, and route call sites.
- E2E/UI flow audit: read-only explorer over `playwright.config.ts`, `e2e/`, and affected UI sections.
- Phase 3: one explorer reviews auth-rate-limit test coverage while the main agent implements D1 helpers.
- Phase 4: one explorer maps frontend network-field usage while the main agent changes API DTOs.
- Phase 6: workers can extract unrelated frontend pieces only if their file ownership is disjoint, such as API client vs Markdown/Toast components.
- Phase 7: one explorer checks dependency classification while the main agent drafts CI.

Avoid sub-agents for:

- Phase 1, because the file set is tiny.
- Phase 2 auth logic, unless the sub-agent is read-only reviewing tests. The security behavior is tightly coupled and should be implemented by one agent.
- Any work touching the same file in parallel, especially `src/App.tsx`.

## Phase 1: E2E Safety

Status: Completed on 2026-06-08.

Goal: remove accidental production mutation risk before any behavior changes.

Likely files:

- `playwright.config.ts`
- `e2e/helpers/auth.ts`
- `README.md`
- `AGENTS.md`

Implementation:

- Make `E2E_BASE_URL` mandatory. Throw a clear config-time error when it is missing, for example: `Set E2E_BASE_URL explicitly, e.g. http://localhost:8788`.
- Remove the production Pages URL as a Playwright default.
- Make `TEST_USERNAME` and `TEST_PASSWORD` mandatory in `e2e/helpers/auth.ts`, retaining `FP_TEST_USERNAME` / `FP_TEST_PASSWORD` only as legacy fallbacks.
- Throw a clear error when credentials are missing.
- Replace README credential examples with placeholders, not real-looking values.
- Update `AGENTS.md` if command examples still mention production defaults or real-looking credentials.

Risk level: Low.

Tests to add/update:

- If practical, add a small unit test around `testCredentials()` by making it testable without importing Playwright runtime side effects. Otherwise keep this as config behavior verified by command failure.
- No E2E mutation test is required for this phase.

Commands to run:

```powershell
npm test
node node_modules/typescript/bin/tsc -b --pretty false
node node_modules/vite/bin/vite.js build
npm run test:e2e
```

The final command should fail clearly when `E2E_BASE_URL` is not set. For an actual E2E run, use:

```powershell
$env:E2E_BASE_URL = "http://localhost:8788"
$env:TEST_USERNAME = "<local-test-username>"
$env:TEST_PASSWORD = "<local-test-password>"
npm run test:e2e
```

Local E2E setup sequence in a first shell:

```powershell
npm run cf:migrate:local
npm run build
npm run dev:worker
```

Then run E2E in a second shell with the explicit env vars shown above.

Acceptance criteria:

- `npm run test:e2e` without `E2E_BASE_URL` fails before tests mutate anything.
- No hard-coded production E2E target remains.
- No hard-coded plausible test credentials remain.
- README and `AGENTS.md` use placeholders only.

Do not change:

- Auth logic.
- E2E test scenarios.
- Production deployment settings.
- D1 migrations.

## Phase 2: Password Reset Hardening

Goal: remove username-only/passwordless login for reset-required accounts while preserving forced password setup.

Likely files:

- `src/api/auth.ts`
- `src/api/auth.test.ts`
- `src/App.tsx`
- Optional: `e2e/home.spec.ts` or new `e2e/auth.spec.ts`

Implementation:

- In `login()`, always verify the submitted password for active users.
- If `password_reset_required = 1`, a valid current temporary password should create a session with `passwordSetupRequired: true`.
- Blank passwords and wrong passwords must return the same generic invalid-login error.
- Keep `updateOwnPassword()` behavior where a reset-required authenticated session may set a new password without entering the current password again.
- In `src/App.tsx`, update login copy that currently tells users to leave the password blank.
- Rename the admin UI action currently labelled `Username login` to `Require password change`.
- Update the activity summary in `src/api/router.ts` if it still says `Enabled username-only login`.

Risk level: High.

Tests to add/update:

- Reset-required user cannot log in with blank password.
- Reset-required user cannot log in with wrong password.
- Reset-required user can log in with the valid temporary password and receives `passwordSetupRequired: true`.
- Reset-required session can set a new password without current password.
- After setting the new password, blank-password login remains impossible and the new password works.
- Existing non-reset login and current-password change behavior still pass.

Commands to run:

```powershell
npm test
node node_modules/typescript/bin/tsc -b --pretty false
node node_modules/vite/bin/vite.js build
```

Acceptance criteria:

- No account can be accessed with username only.
- Admin-created temporary-password flow still works.
- Forced password setup still blocks normal app loading until the password is changed.
- Errors do not reveal whether the username exists or whether reset is required.

Do not change:

- Password hash format.
- Session cookie name or storage model.
- Admin unlock duration.
- Rate limiting. That is Phase 3.

## Phase 3: Auth Rate Limiting

Goal: add lightweight D1-backed throttling for login and admin unlock.

Likely files:

- New `migrations/0008_auth_attempts.sql`
- `src/api/auth.ts`
- `src/api/auth.test.ts`
- Optional: `src/api/types.ts`

Implementation:

- Add a migration:

```sql
CREATE TABLE IF NOT EXISTS auth_attempts (
  key TEXT PRIMARY KEY,
  count INTEGER NOT NULL DEFAULT 0,
  first_seen_at TEXT NOT NULL,
  last_seen_at TEXT NOT NULL
);
```

- Track failures by action, username, and client signal:
  - `login:<username>:<client-signal>`
  - `admin:<username>:<client-signal>`
- Client signal precedence:
  - `CF-Connecting-IP`
  - first value from `X-Forwarded-For`
  - `unknown`
- Policy:
  - 5 failures within 10 minutes are allowed.
  - Further attempts within the window return a generic 429-style auth error.
  - After the window expires, reset the counter.
  - Successful login/admin unlock clears that key.
- Keep all credential errors generic.
- Make helper functions small and testable without needing a real D1 database.

Risk level: Medium-high.

Tests to add/update:

- First through fifth bad login attempts return normal invalid credentials.
- Sixth bad login attempt within 10 minutes is blocked.
- Expired window allows attempts again.
- Successful login clears prior failures.
- Admin unlock failures are counted separately from normal login.
- Client-signal fallback works when headers are absent.

Commands to run:

```powershell
npm test
node node_modules/typescript/bin/tsc -b --pretty false
node node_modules/vite/bin/vite.js build
```

Acceptance criteria:

- Repeated bad login attempts are throttled.
- Admin unlock is throttled.
- Successful authentication clears the relevant attempt key.
- No external service or in-memory-only limiter is introduced.

Do not change:

- Session creation response shape.
- Manual migration policy.
- Phase 2 reset behavior.

## Phase 4: Network Privacy Boundary

Goal: ensure normal household sessions do not receive sensitive network details unless admin-unlocked.

Likely files:

- `src/api/data.ts`
- `src/api/router.ts`
- `src/api/data.test.ts`
- `src/App.tsx`
- Optional: `e2e/home.spec.ts`

Implementation:

- Split network DTOs into member-safe summary and admin detail.
- Member-safe data may include:
  - `wifiName`
  - `wifiSecurity`
  - usage summary if desired
  - non-sensitive deployment note/status
- Admin detail may include:
  - `wifiPassword`
  - `routerUrl`
  - `adminUrl`
  - device details
  - QR payload data
- Make `/api/home` include only member-safe network data.
- Make normal `GET /api/network` member-safe, or add a separate admin-only endpoint such as `/api/network/admin` for full details. Pick one route shape and document it in code/tests.
- Gate full network details with `requireAdminUnlock()`.
- Update frontend rendering so fields that may be absent are hidden cleanly.
- If the Network workspace needs full details, fetch them only after admin unlock or show a locked/admin-required state.

Risk level: Medium.

Tests to add/update:

- Normal authenticated `/api/home` response omits `wifiPassword`, `routerUrl`, `adminUrl`, and device details.
- Normal authenticated network route omits secrets if it remains public to members.
- Admin-unlocked route returns full network details.
- Frontend still handles missing sensitive fields without runtime errors.

Commands to run:

```powershell
npm test
node node_modules/typescript/bin/tsc -b --pretty false
node node_modules/vite/bin/vite.js build
```

Acceptance criteria:

- A normal member session cannot receive Wi-Fi password, router URL, admin URL, or device details from the API.
- Admin-unlocked users can still manage and view full network details.
- Dashboard and network tab remain usable.

Do not change:

- Stored settings keys.
- Admin settings edit fields.
- QR payload format except to hide it when password/detail data is unavailable.

## Phase 5: Data Correctness Fixes

Goal: fix small weather/tide correctness issues after security boundaries are handled.

Likely files:

- `src/App.tsx`
- `src/api/data.ts`
- `src/api/modules.ts`
- `src/api/data.test.ts`
- `src/api/modules.test.ts`

Implementation:

- In weather UI, display `home.weather.current.precipitation` as millimetres, not percent.
- Keep `daily.precipitationChance` and `hourly.precipitationChance` as percentages.
- Use clear labels such as `Rain chance` for probability and `Precipitation` for amount.
- When tides module options change in `updateModules()`, clear `marine-*` cache rows if the `tides` patch changes source or API key.
- Do not clear unrelated weather cache for tide API-key-only changes.
- Alternatively, include a safe hash of relevant tide source/options in the marine cache key, but the first pass should prefer targeted cache invalidation.

Risk level: Low-medium.

Tests to add/update:

- Unit test that tide option changes clear marine cache and leave unrelated cache rows alone.
- Unit test that non-tide module option changes do not clear marine cache.
- UI label change can be covered by E2E only if a stable weather fixture exists; otherwise TypeScript/build coverage is acceptable.

Commands to run:

```powershell
npm test
node node_modules/typescript/bin/tsc -b --pretty false
node node_modules/vite/bin/vite.js build
```

Acceptance criteria:

- Current precipitation is never labelled as `% rain`.
- Probability remains `%` only for probability fields.
- Tide source/API-key changes cannot serve stale marine cache.

Do not change:

- Weather/marine upstream providers.
- Weather cache TTL.
- Location-based cache invalidation behavior.
